## 2026-11-20 (M2 blocker and fallback)

- Hit Open-Meteo's undocumented hourly request limit while fetching 30-year history for the 319 unique top-2 candidate cells (10-coordinate batches). Response: `{"error":true,"reason":"Hourly API request limit exceeded. Please try again in the next hour."}`. Confirmed with a single-point test request immediately after stopping the pipeline script, so this is a real account/IP-level hourly cap, not a bug in the retry logic. No specific fallback for this is written in docs/build-plan.md, so per the general 20-minute rule: stopped the blocked step, logged it here, and moved on to other milestones that do not need fresh API calls (web app scaffold, alert text, CAP XML, backtest write-up) while the hourly window resets. Will resume `npm run pin:cells` and `npm run climatology` once the limit clears, with a smaller SAMPLE_PER_STATE and a longer throttle to stay well under whatever the real cap is, since it is unverified and undocumented.
- Already-cached responses (forecast for all ~1978 unique window points, plus 1 of 32 history batches) are kept in data/cache/ and will be reused on the next run, so no completed work is lost.
- Changed pin-cells.ts to keep only the top 1 candidate cell by 7-day forecast mean per facility, not the top 2 the plan describes, to roughly halve the number of unique cells needing a full 30-year history pull before resuming after the hourly cap. Old value: top 2 (then choose by higher 30-year median). New value: top 1 (median is still computed and stored, but there is no second candidate to compare against). Reason: fit the remaining hackathon time budget after the rate-limit blocker above. This does not change any alert threshold, only how many forecast-ranked candidates are considered before pinning.
- Increased the history-fetch throttle from 1500 ms to 4000 ms (HISTORY_THROTTLE_MS in pipeline/lib/openmeteo.ts) to stay further under whatever the real hourly cap is.

## 2026-11-20 (cache keying bug, plateau detection bug)

- Found and fixed a real caching bug: fetchDailyBatch cached by the whole batch query string (all points joined), so the same point requested in a differently-ordered or differently-sized batch (which happened between pin-cells.ts and climatology.ts) was a cache miss and would have re-spent the same tight hourly quota on data already paid for. Changed to cache per individual point instead. Wrote pipeline/migrate-cache.ts, a one-off that rebuilt per-point cache entries from the existing batch-keyed cache files (3268 point entries recovered from 41 files) with no new API calls.
- Found and fixed a real logic bug in the Lokoja plateau detector (pipeline/lib/stats.ts detectPlateaus): it flagged a cell as low-confidence if the series had ANY run of 3+ identical values ANYWHERE, independently checked against whether the series separately had any value at or above p99. Those two conditions are almost always both true for 30 years of daily data (long dry-season runs of identical low values are normal and harmless), so every one of the first 50 real cells got flagged, which is not plausible and was caught by inspecting the actual output rather than trusting the summary count. Added detectTopPlateau, which only flags a run of 3+ identical values when the repeated value itself is at or above the threshold, with 3 new unit tests distinguishing a dry-season zero plateau from a genuine high-value plateau. Rerunning climatology.ts after the fix: 11 of 50 real cells flagged, not 50.

## 2026-11-20 (heat/cold layer: verified Open-Meteo weather API terms before building)

- Coordinator asked for a new experimental heat/cold layer (not the rainfall idea from an earlier message, which is dropped). Before building anything, verified Open-Meteo's weather forecast API (api.open-meteo.com/v1/forecast) and historical archive API (archive-api.open-meteo.com/v1/archive) the same way the flood API was verified in docs/claude.md: fetched https://open-meteo.com/en/terms directly. Confirmed free, keyless use for non-commercial purposes under CC-BY 4.0, with published rate limits of under 10,000 calls/day, 5,000/hour, 600/minute, per IP and application, much more generous than whatever undocumented limit the flood API subdomain enforced on this session (the terms page explicitly reserves the right to block IPs that misuse the service, which may explain why flood-api.open-meteo.com specifically got so restrictive after this session's many 429s, if the two subdomains share a block list). Both test requests (forecast and archive, Enugu coordinates) returned real data with no key.
- Design choice for this layer: snap each facility to a 0.5 degree grid cell (much coarser than the river grid's ~0.05 x 0.1 degree), rather than querying each facility's exact coordinate. Temperature and heat stress vary smoothly over tens of kilometers in Nigeria's climate, unlike river discharge, which is drainage-basin-specific, so a coarse shared cell is a defensible simplification here and keeps the API cost bounded regardless of how many facilities this layer eventually covers (unlike the river pilot, this is meant to cover all ~46,140 facilities nationwide, not a 150-400 pilot).

## 2026-11-20 (coverage-loss bug found and fixed)

- Found a serious bug after reordering pin-cells.ts to prioritize unreached states: a rerun pinned only 11 facilities and the coverage table showed 0 for Kogi, Niger, Kwara and Nasarawa, the 4 states with real data from the previous run. Root cause: fetchForecast/fetchHistory's "stop after a 429" logic skipped the ENTIRE remaining chunk list once hit, including chunks that would have been free cache hits for cells already fetched in an earlier session. Combined with the new state-priority order (unreached states first), the previously-successful cells were queued later and never even checked against the cache this run, even though they were sitting on disk. Fixed in two places: (1) fetchDailyBatch now takes an `allowNetwork` flag; once the limit is hit, every remaining chunk is still checked against the cache, only the network call is skipped. (2) pin-cells.ts now loads the existing data/pins.json and merges this run's results on top, instead of overwriting the file from only this run's output, so a pin can never silently disappear because a later run's candidate order didn't reach it in time.

## 2026-11-20 (rate limit, second hit, resilience changes)

- The hourly limit cleared, then was hit again almost immediately. Root cause: the repeated single-point curl checks used to test whether the limit had cleared, plus the Monitor tool's own 45-second poll loop, were themselves counted against the same hourly quota, so checking for the limit to clear was consuming it. Fixed by widening the Monitor poll interval to 5 minutes and stopping manual interim curl checks.
- Changed pipeline/lib/openmeteo.ts: fetchWithRetry no longer retries on 429 (each retry is itself a request that burns more of the same tight quota); it now fails fast. fetchHistory no longer throws on the first failed chunk; it marks the quota as exhausted for the rest of that run, fills remaining points with null, and returns what succeeded so far, so a run that gets rate-limited partway through still saves partial progress instead of losing everything.

- Removed the `.gitignore` rule that excluded `web/public/data/*.json`. Vercel's static build (`vercel.json`'s buildCommand) only runs `npm run build` inside web/, it does not call the pipeline, so if the generated per-state facility files, latest.json, and alerts-today.json were gitignored, a fresh checkout would deploy with no data at all. The GitHub Actions daily cron is what keeps these files fresh and commits them; Vercel then just serves whatever is checked in. These files are small (per-state facility subsets of the pilot, not the full 46,140-row national file), unlike data/facilities.json, which stays gitignored.

## 2026-11-20 (facility markers never rendered on the map, found via live browser check)

- Checked the live deploy with a real browser (Claude in Chrome, Brave) instead of only reading code: the map loaded, zoomed to the right state, and the data counts were correct, but zero facility markers ever appeared anywhere on the map, with no console error.
- Root cause: `MapView.tsx` called `map.addImage(id, canvas as unknown as HTMLImageElement)`, passing a raw `HTMLCanvasElement`. MapLibre GL's `addImage` only accepts `HTMLImageElement | ImageBitmap | ImageData | {width, height, data}` (confirmed in `node_modules/maplibre-gl/dist/maplibre-gl.d.ts`), not a canvas. The `as unknown as` cast satisfied `tsc` but the runtime call silently did nothing: no marker image was ever registered, so every `icon-image` reference pointed at a missing image and nothing drew. No console warning surfaced in this setup, so the type check and a successful build both looked clean while the feature was completely broken.
- Fixed by pulling the canvas's pixels out as `ImageData` (`ctx.getImageData(0, 0, w, h)`) before calling `addImage`, which is one of the accepted types. Verified live in the browser afterward: individual facility markers and cluster bubbles both render correctly.
- Lesson: an `as unknown as X` cast is a signal to go check the real runtime contract, not just satisfy the compiler. Logged so a future session does not reach for the same shortcut with a different library.

## 2026-11-20 (the real root cause: missing glyphs property crashed the map's render loop)

- Found via a browser console check (not visible in any of the earlier network/DOM checks): every page load threw `Error: layers.cluster-count.layout.text-field: use of "text-field" requires a style "glyphs" property`, originating inside MapLibre's own render loop (`F.Map._render`), not at the point we called `addLayer`. Our inline style object never set `glyphs`, but the cluster-count layer uses `text-field` to show the point count, which needs one.
- This explains the whole cluster of flaky symptoms from this session: markers rendering on some loads and not others, tiles appearing blank, screenshots behaving inconsistently. An uncaught exception repeating inside a WebGL render loop is a plausible cause for all of it, not three separate bugs.
- Fixed by adding a free, keyless, CORS-open glyph source (`https://fonts.openmaptiles.org/{fontstack}/{range}.pbf`, logged in ATTRIBUTIONS.md) as the style's `glyphs` property, and setting an explicit `text-font: ["Open Sans Regular"]` on the cluster-count layer to match a font that server actually has.
- Lesson: `read_console_messages` should be the first thing checked when a WebGL/canvas-based component misbehaves, before chasing DOM/CSS/network theories. It took far longer to find this because the console wasn't checked early enough.
